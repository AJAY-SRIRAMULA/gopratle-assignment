# GoPratle Requirements — Event Requirement Posting Flow

A four-step, category-aware form for posting **Event Planner**, **Performer** or **Crew** requirements.
Next.js frontend → Express API → MongoDB (via Mongoose).

Built for the GoPratle Full-Stack Developer Intern assignment. It is an independent project, **not an official GoPratle product**.

## Key features

- Four steps: Event basics → Requirements → More details → Review & submit, with an accurate progress indicator.
- Steps 2 and 3 change completely per category (planner / performer / crew). Field definitions live in one config (`frontend/lib/constants.js`) that drives the form, validation, payload and review.
- Per-category answer storage: switching category never mixes data, and switching back restores what you typed. Only the selected category is submitted.
- Frontend validation per step plus a full re-validation on submit; independent **server-side validation** that whitelists fields per category.
- Real persistence: `POST /api/requirements` → validation → Mongoose → MongoDB → `201` with the generated ID shown on the success screen.
- Loading state, duplicate-submit protection, server/network error handling that preserves the form.
- Accessible: labels, `aria-invalid`/`aria-describedby`, keyboard-operable category cards, visible focus, non-colour selection cues.

## Database schema

One collection, `requirements`:

| Field | Type | Notes |
|---|---|---|
| `eventName`, `eventType`, `location` | String | required, trimmed, length-limited |
| `eventTypeOther` | String | only when `eventType` = "Other" |
| `startDate`, `endDate` | String `YYYY-MM-DD` | strings on purpose: no timezone shifting. Single-day events store the same date twice |
| `venue` | String | optional |
| `category` | `planner` \| `performer` \| `crew` | enum, indexed |
| `details` | Object | category-specific required answers (below) |
| `additionalDetails` | Object | category-specific optional text |
| `createdAt`, `updatedAt` | Date | generated by Mongoose/server |

`details` is a flexible object, so a `pre('validate')` hook re-runs the category-aware validator before every save. A planner document cannot contain crew fields, and the category must match its details.

- **planner**: `planningType, guestCount, budget, services[], servicesOther?, preferredExperience`
- **performer**: `performanceType, performanceTypeOther?, durationMinutes, performerCount, style, budget, technicalRequirements?`
- **crew**: `crewRole, crewRoleOther?, crewCount, durationHours, budget, equipmentRequirements?, additionalRoleRequirements?`

## API

All responses are JSON: `{ success, message?, data?, errors? }`.

| Method & path | Purpose | Success | Errors |
|---|---|---|---|
| `GET /api/health` | liveness + DB readiness | `200` `{status:"ok", database:"connected"}` | `503` if the DB is not connected |
| `POST /api/requirements` | create | `201` | `400` malformed JSON, `413` body > 50 kb, `415` not JSON, `422` validation (`errors` keyed by field path), `503` DB unavailable, `500` unexpected |
| `GET /api/requirements/:id` | read one (for verification) | `200` | `400` bad ID, `404` not found, `503` |

There is deliberately **no list endpoint**.

Example request (`POST /api/requirements`):

```json
{
  "eventName": "Wedding Celebration", "eventType": "Wedding",
  "startDate": "2026-12-15", "endDate": "2026-12-16",
  "location": "Hyderabad", "venue": "Grand Convention Hall",
  "category": "planner",
  "details": { "planningType": "Full event planning", "guestCount": 500, "budget": 300000,
               "services": ["Decoration", "Catering coordination"], "preferredExperience": "Experienced" },
  "additionalDetails": { "theme": "Traditional" }
}
```

Example responses:

```json
// 201
{ "success": true, "message": "Requirement created successfully",
  "data": { "id": "<mongo ObjectId>", "category": "planner", "eventName": "Wedding Celebration", "createdAt": "<ISO timestamp>" } }

// 422
{ "success": false, "message": "Validation failed", "errors": { "details.budget": "Budget cannot be negative" } }
```

## Prerequisites

Node.js 18+ (built and tested on Node 22), npm, a MongoDB database (Atlas free tier is fine), Git.
The frontend and backend are **separate apps with separate `npm install`s** — use two terminals.

## Local setup (Windows PowerShell)

### 1. MongoDB Atlas
1. Create a free cluster at <https://cloud.mongodb.com>.
2. *Database Access* → add a user (username + password) with the **readWrite** role on one database only.
3. *Network Access* → allow your IP for local work. For Render (no fixed outbound IP) you will need `0.0.0.0/0`; with a strong password and a least-privilege user that is a common free-tier trade-off — tighten it if you move to a paid plan with fixed IPs.
4. *Connect → Drivers* → copy the connection string and add a database name, e.g. `mongodb+srv://USER:PASS@cluster0.xxxxx.mongodb.net/gopratle?retryWrites=true&w=majority`. URL-encode special characters in the password.

### 2. Backend
```powershell
cd backend
npm install
copy .env.example .env      # edit MONGODB_URI
npm run dev                 # or: npm start
```
`backend/.env`:
```
PORT=5000
NODE_ENV=development
MONGODB_URI=<your connection string>
FRONTEND_URL=http://localhost:3000     # comma-separate multiple origins, no trailing slash
```
Check it: `curl http://localhost:5000/api/health` → `{"success":true,"status":"ok","database":"connected",...}`

### 3. Frontend (second terminal)
```powershell
cd frontend
npm install
copy .env.example .env.local
npm run dev                 # http://localhost:3000
```
`frontend/.env.local`: `NEXT_PUBLIC_API_URL=http://localhost:5000`

### 4. Submit a test requirement
Open <http://localhost:3000>, complete the four steps, submit. The success screen shows the saved ID.

### Verify persistence in MongoDB
1. With the backend running and connected: `node backend/scripts/smoke.mjs` — creates one requirement per category, reads each back by ID, checks the stored category, and checks a mismatched payload is rejected.
2. In Atlas → *Browse Collections* → `gopratle.requirements`, find the document whose `_id` matches the ID on the success screen and confirm `category` and `details`.

## Testing

```powershell
cd backend;  npm test      # 44 tests, no database required
cd frontend; npm test      # 33 tests
cd frontend; npm run build # production build
```

What the tests do and do not prove:
- Backend HTTP tests stub the database layer; they prove routing, validation, status codes, CORS, error shapes and that the controller hands the right document to `Requirement.create`. They do **not** prove data reaches MongoDB — that is what `smoke.mjs` is for.
- Frontend tests render the real wizard in jsdom and mock only `fetch`. They are not a substitute for a real-browser and phone check.
- Edge cases covered by automated tests: missing/whitespace/over-long name, missing type/date/location, invalid & impossible dates, end < start, blank venue accepted, missing/invalid category, missing required fields per category, negative budget/guests, zero performers/crew, non-numeric values, over-long text, cross-category fields rejected, malformed JSON, wrong content type, oversized body, DB down, DB error without secret leakage, duplicate submit clicks, category switching, network failure, server validation error, invalid ID on GET.
- Browser refresh: in-progress answers are **intentionally discarded** (nothing is written to localStorage, to avoid persisting data unnecessarily).

## Deployment (not yet done — your accounts are required)

### Backend → Render
1. Push to GitHub (below). Render → *New Web Service* → connect the repo.
2. Root directory `backend`, build `npm install --omit=dev`, start `npm start` (or use `render.yaml`).
3. Environment variables: `NODE_ENV=production`, `MONGODB_URI=<Atlas string>`, `FRONTEND_URL=https://<your-vercel-domain>` (set after step in Vercel; redeploy after changing). Do not set `PORT`; Render provides it.
4. Verify `https://<backend>/api/health` shows `"database":"connected"`. Free tier sleeps when idle; the first request can take ~30–60 s (the frontend timeout allows 60 s).

### Frontend → Vercel
1. Vercel → *Add New Project* → import the repo → **Root Directory: `frontend`**.
2. Environment variable: `NEXT_PUBLIC_API_URL=https://<your-render-backend>` (build-time; redeploy after changing).
3. Deploy, open the URL, submit one requirement of each category, then confirm the documents in Atlas.
4. Put the Vercel URL into the backend's `FRONTEND_URL` (exact origin, no trailing slash; preview deployments are different origins and need to be added too).

## Decisions and assumptions

- Event dates may be in the past (no business rule was given). Dates are `YYYY-MM-DD` strings end to end.
- Crew duration minimum is 0.5 hours; performance duration minimum is 1 minute; upper limits: 100,000 guests, ₹10 crore budget, 24 h performance, 168 h crew, 500 performers, 1,000 crew.
- "Other" choices (event type, planner service, performance category, crew role) require a short custom description.
- Planner "experience" is the requester's preference only; nothing claims a verified professional.
- Fonts are the system stack (no Google Fonts) so builds never need external network access.

## Known limitations

- `POST /api/requirements` is **public and unauthenticated** (authentication is out of scope). CORS only controls which *browsers* may call it; it does not stop scripts or curl. There is no rate limiting, so spam is possible; add rate limiting/CAPTCHA before real use.
- No contact details are collected, so a posted requirement cannot yet be linked to a person.
- No admin/list view; verification is via the ID or MongoDB itself.
- Persistence, deployment and real-device layout have not been verified by the author of this scaffold; see the status table.

## Potential improvements

Rate limiting and bot protection, contact details + email confirmation, idempotency keys for retried submissions, draft autosave (with consent), richer date/location pickers, end-to-end browser tests (Playwright), CI running both test suites, structured logging.
